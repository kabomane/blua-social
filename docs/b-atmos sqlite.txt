ARCHITECTURE SQLITE MVP — PROJET RÉSEAU SOCIAL ASYNCHRONE
================================================================================


1. OBJECTIF
================================================================================

Pour le MVP, utiliser UNE SEULE base SQLite :

    data/app.db

avec :

    PRAGMA journal_mode = WAL;
    PRAGMA foreign_keys = ON;
    PRAGMA busy_timeout = 5000;

Pourquoi une seule DB au départ :

- garder les transactions simples ;
- éviter de répartir une même opération métier sur plusieurs fichiers ;
- permettre à SQLite de garantir l'atomicité des opérations ;
- simplifier énormément le développement du MVP ;
- WAL permet aux lectures de continuer pendant les écritures ;
- les écritures seront courtes et relativement peu nombreuses ;
- aucun besoin d'optimiser prématurément pour des millions d'utilisateurs.

5. FRIENDSHIPS
================================================================================

Le réseau repose sur des AMITIÉS RÉCIPROQUES, pas sur followers/following.


CREATE TABLE friendships (
    user_a_id TEXT NOT NULL,
    user_b_id TEXT NOT NULL,

    status TEXT NOT NULL,
    created_at INTEGER NOT NULL,

    PRIMARY KEY (user_a_id, user_b_id),

    FOREIGN KEY (user_a_id) REFERENCES users(id),
    FOREIGN KEY (user_b_id) REFERENCES users(id)
);


CREATE INDEX friendships_a
ON friendships(user_a_id);

CREATE INDEX friendships_b
ON friendships(user_b_id);


Important :

Toujours normaliser les IDs pour éviter :

    Alice / Bob

et :

    Bob / Alice

comme deux relations différentes.

Par exemple :

    user_a_id = min(user1, user2)
    user_b_id = max(user1, user2)

9. MESSAGE != DELIVERY
================================================================================

C'est une séparation fondamentale.

Un MESSAGE représente :

    "ce qui a été dit"

Une DELIVERY représente :

    "le voyage de ce message vers une destination"


Exemple :

Alice publie :

    "Salut !"

                        MESSAGE M1
                            |
               +------------+------------+
               |            |            |
               v            v            v
             Bob          Emma         Lucas
             Paris        Tokyo         Berlin
               |            |            |
               v            v            v
             D1           D2           D3


Un seul message peut donc posséder plusieurs deliveries.

     |

     |
     v
    sauvegarde tout


Ensuite :

    AUCUN recalcul complet.


Exemple :

    sent_at       = 14:00
    delivered_at  = 18:37

Par exemple :

    seed = message_id

    la vitesse

================================================================================
12. PAS BESOIN DE WORKER POUR FAIRE "ARRIVER" LES MESSAGES
================================================================================

Éviter pour le MVP :

    message envoyé
        |
        v
    attendre 3 heures
        |
        v
    worker
        |
        v
    UPDATE status = DELIVERED


À la place :

Le temps détermine directement la visibilité.


Message existant :

    sent_at      = 14:00
    delivered_at = 18:00


À 16:00 :

    delivered_at > maintenant

Donc :

    invisible


À 18:01 :

    delivered_at <= maintenant

Donc :

    visible


Exemple SQL :

SELECT *
FROM deliveries
WHERE recipient_id = ?
  AND delivered_at <= unixepoch()
ORDER BY delivered_at DESC;


Avantages :

- aucune écriture nécessaire au moment de l'arrivée ;
- beaucoup moins de contention SQLite ;
- pas besoin de scheduler complexe ;
- pas besoin de Redis ;
- pas besoin de queue ;
- pas besoin de worker permanent ;
- architecture déterministe.


================================================================================
13. PIGEON = RESSOURCE TEMPORELLE
================================================================================

Même logique pour les pigeons.

Ne pas stocker constamment :

    AVAILABLE
    BUSY
    AVAILABLE
    BUSY


Stocker plutôt l'utilisation d'un pigeon.


CREATE TABLE pigeon_actions (
    id TEXT PRIMARY KEY,

    user_id TEXT NOT NULL,
    message_id TEXT NOT NULL,

    action_type TEXT NOT NULL,

    started_at INTEGER NOT NULL,
    busy_until INTEGER NOT NULL,

    FOREIGN KEY (user_id) REFERENCES users(id),
    FOREIGN KEY (message_id) REFERENCES messages(id)
);


CREATE INDEX pigeon_actions_active
ON pigeon_actions(user_id, busy_until);


Pour connaître les pigeons actuellement utilisés :

SELECT COUNT(*)
FROM pigeon_actions
WHERE user_id = ?
  AND busy_until > unixepoch();


Si l'utilisateur possède 5 pigeons :

    total = 5

    active = SELECT COUNT(...)

    available = total - active


Exemple :

    total pigeons : 5
    occupés        : 3
    disponibles    : 2


Pas besoin d'UPDATE pour rendre le pigeon disponible.

Lorsque :

    busy_until <= maintenant

il est automatiquement considéré comme disponible.

14. PIGEON = ACTION DE COMMUNICATION
================================================================================

Important :

Un pigeon représente une ACTION DE COMMUNICATION.

Pas forcément une livraison physique par destinataire.


Exemple :

Alice fait un post Home :

    coût :
        1 pigeon


Mais le backend peut générer :

                  MESSAGE
                     |
        +------------+------------+
        |            |            |
        v            v            v
       Bob          Emma         Lucas


Donc :

    1 pigeon_action

mais éventuellement :

    N deliveries


Actions consommant un pigeon :

    envoyer un DM
    publier sur Home
    envoyer dans une branche
    répondre
    transmettre


================================================================================
15. TRANSACTION D'ENVOI
================================================================================

L'envoi complet doit rester atomique.

Même fichier SQLite = transaction simple.


BEGIN IMMEDIATE;

    1. vérifier nombre de pigeons disponibles

    2. INSERT message

    3. INSERT pigeon_action

    4. INSERT delivery

       éventuellement :

       INSERT delivery
       INSERT delivery
       INSERT delivery

COMMIT;


Pseudo Node.js :

await db.exec("BEGIN IMMEDIATE");

try {

    // vérifier capacité pigeon

    // créer message

    // créer pigeon_action

    // créer deliveries

    await db.exec("COMMIT");

} catch (err) {

    await db.exec("ROLLBACK");

    throw err;
}


Cela garantit qu'on ne peut pas avoir :

    pigeon occupé
    mais message inexistant


ou :

    message créé
    mais aucune delivery

Éviter :

    users.db

    UPDATE pigeons.db

    INSERT messages.db

RÈGLE :

    TOUT CE QUI DOIT ÊTRE ATOMIQUE
    DOIT RESTER DANS LE MÊME FICHIER DB.


Donc au minimum :

    messages
    deliveries
    pigeon_actions

doivent rester ensemble.

19. CONFIGURATION DU SYSTÈME DE LIVRAISON
================================================================================

Les données globales et relativement statiques restent dans le CODE :

    oiseaux
    hubs
    gateways
    règles de livraison


Structure :

delivery-engine/
|
├── birds.js
├── hubs.js
├── rules.js
├── haversine.js
├── bird.js
└── post.js


Exemple :

export const DELIVERY_RULES = {

    bird: {
        speedKmH: 45,
        routeFactor: 1.10,
        flightHoursPerDay: 12,
        speedVariance: 0.08
    },

    post: {
        collectionMinHours: 2,
        collectionMaxHours: 6,
        planeSpeedKmH: 750
    }

};


Avantages :

- facilement versionnable avec Git ;
- simple à modifier ;
- pas besoin de requête SQL ;
- logique métier regroupée ;
- facilement testable.


IMPORTANT :

Chaque delivery sauvegarde les résultats réellement calculés.

Ainsi :

    rules v1
        vitesse = 45 km/h

Message envoyé aujourd'hui :
        reste basé sur 45 km/h


Puis :

    rules v2
        vitesse = 50 km/h

Les nouveaux messages utilisent 50 km/h.

Les anciens voyages ne changent PAS.

21. RÈGLE IMPORTANTE : TRANSACTIONS COURTES
================================================================================

Bon :

BEGIN;

INSERT message;
INSERT pigeon_action;
INSERT deliveries;

COMMIT;


Mauvais :

BEGIN;

INSERT message;

await appelHTTPQuiPrend5Secondes();

INSERT delivery;

COMMIT;


Ne jamais garder une transaction ouverte pendant :

- appel HTTP externe ;
- calcul long ;
- attente artificielle ;
- traitement d'image ;
- timeout ;
- opération réseau.


Calculer le trajet AVANT ou pendant une opération CPU très courte,
puis effectuer rapidement la transaction SQLite.

26. PRINCIPE CENTRAL DU BACKEND
================================================================================

Beaucoup d'états ne nécessitent PAS d'UPDATE.

Ils sont dérivés du temps.


MESSAGE VISIBLE :

    delivered_at <= now


PIGEON DISPONIBLE :

    busy_until <= now


NOTIFICATION VISIBLE :

    visible_at <= now


Donc le temps remplace énormément de :

    workers
    UPDATE
    cron jobs
    queues


Ce point est particulièrement intéressant avec SQLite,
car il réduit fortement le nombre d'écritures concurrentes.

27. ARCHITECTURE MVP RETENUE
================================================================================

STACK :

    Node.js
        +
    sqlite3 / wrapper Promise
        +
    SQLite
        +
    WAL


DATABASE :

    UNE SEULE app.db


TABLES PRINCIPALES :

    users
    friendships
    branches
    branch_memberships
    messages
    deliveries
    pigeon_actions
    notifications


CONFIGURATION MÉTIER :

    birds.js
    hubs.js
    rules.js


PRINCIPES :

    1. Message != Delivery.

    2. Un pigeon représente une action de communication.

    3. Une action peut générer plusieurs deliveries.

    4. Les voyages sont calculés une seule fois à l'envoi.

    5. delivered_at détermine la visibilité.

    6. busy_until détermine la disponibilité des pigeons.

    7. visible_at détermine l'apparition des notifications.

    8. Pas de worker nécessaire pour faire arriver un message au MVP.

    9. Les écritures SQLite doivent être très courtes.

    10. Utiliser WAL.

    11. Garder les opérations atomiques dans le même fichier DB.

    12. Faire du fan-out on read pour la Home au MVP.

    13. Ne découper la DB que lorsqu'un problème réel de contention apparaît.

    14. Ne pas optimiser pour des millions d'utilisateurs avant d'avoir validé
        le produit avec les premiers utilisateurs.

28. ADDENDUM IMPÉRATIF — DIFFUSION V3
================================================================================

Cette section prévaut sur toutes les sections antérieures qui évoquent une
delivery par destinataire, un delivered_at individuel, ou un fan-out de
deliveries pour Home ou Branch.

Une delivery représente désormais seulement un trajet physique vers une
destination unique : CUI-TO-CUI, auteur -> branche, ou auteur -> hub Home.
Une diffusion à partir d'une branche ou d'un hub Home utilise broadcasts et
bitmaps : elle ne crée jamais N deliveries utilisateur.

Historique des membres de branche et slots stables :

CREATE TABLE branch_membership_periods (
    id TEXT PRIMARY KEY,
    branch_id TEXT NOT NULL,
    user_id TEXT NOT NULL,
    slot_index INTEGER NOT NULL,
    role TEXT NOT NULL DEFAULT 'MEMBER',
    joined_at INTEGER NOT NULL,
    left_at INTEGER,
    UNIQUE(branch_id, slot_index),
    FOREIGN KEY (branch_id) REFERENCES branches(id),
    FOREIGN KEY (user_id) REFERENCES users(id)
);

CREATE INDEX membership_period_lookup
ON branch_membership_periods(branch_id, user_id, joined_at, left_at);

slot_index est attribué par branche, stable et jamais réutilisé. Il ne dépend
jamais de l'ordre physique des lignes SQLite.

Historique des amitiés, nécessaire pour les droits Home :

CREATE TABLE friendship_periods (
    id TEXT PRIMARY KEY,
    user_a_id TEXT NOT NULL,
    user_b_id TEXT NOT NULL,
    started_at INTEGER NOT NULL,
    ended_at INTEGER,
    FOREIGN KEY (user_a_id) REFERENCES users(id),
    FOREIGN KEY (user_b_id) REFERENCES users(id)
);

CREATE INDEX friendship_period_lookup
ON friendship_periods(user_a_id, user_b_id, started_at, ended_at);

Les IDs sont normalisés comme dans friendships. Une période couvre une
diffusion lorsque started_at <= distribution_started_at < ended_at, ou quand
ended_at vaut NULL. La table friendships peut rester la relation active rapide,
mais friendship_periods fait autorité pour l'historique.

Slots stables pour l'audience Home d'un auteur :

CREATE TABLE home_recipient_slots (
    publisher_user_id TEXT NOT NULL,
    recipient_user_id TEXT NOT NULL,
    slot_index INTEGER NOT NULL,
    assigned_at INTEGER NOT NULL,
    PRIMARY KEY (publisher_user_id, recipient_user_id),
    UNIQUE (publisher_user_id, slot_index),
    FOREIGN KEY (publisher_user_id) REFERENCES users(id),
    FOREIGN KEY (recipient_user_id) REFERENCES users(id)
);

Le slot est conservé après une fin d'amitié afin que les anciens broadcasts
restent interprétables. Il n'est jamais réutilisé.

CREATE TABLE broadcasts (
    id TEXT PRIMARY KEY,
    message_id TEXT NOT NULL UNIQUE,
    audience_type TEXT NOT NULL, -- HOME ou BRANCH
    origin_type TEXT NOT NULL,   -- HUB ou BRANCH
    origin_id TEXT NOT NULL,
    origin_lat REAL NOT NULL,
    origin_lon REAL NOT NULL,
    method TEXT NOT NULL,        -- BIRD ou POST
    distribution_started_at INTEGER NOT NULL,
    settled_at INTEGER NOT NULL,
    FOREIGN KEY (message_id) REFERENCES messages(id)
);

CREATE INDEX broadcasts_active
ON broadcasts(audience_type, distribution_started_at, settled_at);

CREATE TABLE broadcast_bitmap_chunks (
    broadcast_id TEXT NOT NULL,
    chunk_index INTEGER NOT NULL,
    received_bits BLOB NOT NULL,
    PRIMARY KEY (broadcast_id, chunk_index),
    FOREIGN KEY (broadcast_id) REFERENCES broadcasts(id)
);

Un chunk contient exactement 512 bits (64 octets). Le backend pose un bit dans une
transaction courte et atomique seulement après avoir autorisé le lecteur. Un
bit signifie « reçu / déverrouillé », jamais « lu ».

Ce format réduit la contention : deux réceptions simultanées n'écrivent le même
chunk que si leurs slots appartiennent au même groupe de 512 utilisateurs.

    chunk_index = floor(slot_index / 512)
    bit_index   = slot_index % 512

Lecture d'une Home ou d'une branche avant settled_at :

    1. vérifier l'éligibilité historique à distribution_started_at ;
    2. si bit reçu = 1, retourner le message ;
    3. sinon calculer l'arrivée depuis le hub/la branche vers users.latitude /
       users.longitude, dernière position connue ;
    4. si arrivée atteinte, poser le bit et retourner le message ;
    5. sinon ne pas retourner le contenu.

Pour une branche, l'éligibilité exige une période joined_at <=
distribution_started_at < left_at (ou left_at NULL). Pour Home, elle exige
l'amitié existante à distribution_started_at. Un nouveau membre ou nouvel ami
ne reçoit pas les anciens messages.

Quand now >= settled_at, supprimer broadcast_bitmap_chunks. L'accès des
personnes historiquement éligibles ne requiert alors plus de bitmap. settled_at
utilise une borne maximale mondiale versionnée par méthode, jamais la position
actuelle d'un lecteur.

Les premières deliveries auteur -> branche/hub restent calculées une seule
fois à l'envoi. Le calcul vers un lecteur dont le bit vaut 0 est, lui, évalué
à la lecture avec sa dernière position connue. Pour un pigeon, la seed doit
inclure message_id + recipient_user_id. Une fois le bit posé, le message ne
disparaît jamais après une mise à jour de position.

CUI-TO-CUI — PURGE DE DELIVERY
-------------------------------

Un cui-to-cui crée une seule delivery physique directe vers recipient_user_id.
À l'envoi, son arrivée calculée est aussi copiée dans messages.available_at.
La lecture devient alors :

    type = 'DIRECT'
    AND recipient_user_id = lecteur.id
    AND available_at <= now

Après l'arrivée, la delivery détaillée peut être supprimée lors d'un nettoyage
différé : messages.available_at conserve le droit de lecture, tandis que la
timeline, la vitesse et la route ne saturent pas deliveries. Il ne faut pas
attendre un worker exact à l'heure d'arrivée : la purge peut être opportuniste
ou périodique. Une delivery directe n'est jamais remplacée par un indicateur
« arrivée pour toute la Terre » ; elle concerne un seul destinataire.

PRINCIPES V3 :

    1. Message = un contenu stocké une seule fois.
    2. Home et Branch = 0 delivery individuelle de diffusion.
    3. CUI-TO-CUI = delivery directe temporaire ; available_at reste dans le
       message après purge de la delivery.
    4. Le backend décide l'accès ; le client ne le calcule pas seul.
    5. users.location_checked_at limite la demande GPS à une fois par 24 h
       au premier plan, sans suivi d'arrière-plan.
    6. Les bitmap chunks sont temporaires ; les relations historiques restent.
